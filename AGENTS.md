# Erskine Duenas, Portfolio (portfolio-next)

## Stack

- **Language / Runtime**: TypeScript, Node 20.9+ (Next 16's minimum)
- **Framework**: Next.js 16 (App Router, Turbopack, exact version pinned in `package.json`), React 19
- **Key dependencies**: Tailwind CSS, shadcn/ui (Radix primitives), Framer Motion (`motion` package), react-icons, @vercel/analytics; studio only: Neon Postgres (`@neondatabase/serverless`), Drizzle ORM (`drizzle-orm`, `drizzle-kit`), private Vercel Blob (`@vercel/blob`), `server-only`
- **Package manager**: npm

## Build approach

Tracer Bullet (each feature is built complete and working end to end before moving to the next). Source: the `docs/scope/scope.md` header.

## Specs

Stored in `docs/specs/`. Format: `docs/specs/NNNN-title.md`, or a directory `docs/specs/NNNN-title/` with `index.md` (build spec), `rationale.md`, and `verify.md` (the `/check verify` checklist).

## Project tracking

`docs/scope/scope.md` is the pipeline's real operating memory (the skills read/write it directly). Jira project `DP` (dev-portfolio, site `vital-stats.atlassian.net`) mirrors it for day to day tracking: Epics = phases (`DP-1` existing, `DP-2` next slice, `DP-32` products page, `DP-33` studio), Stories = features, Subtasks = the exact skill commands (`Design it (/architect)`, `Build it (/develop)`, `Verify it (/check verify)`). After any `/scope`, `/architect`, `/develop`, or `/check verify` run that changes a feature's status, mirror the change into the matching Jira issue (status transition, new subtask, or updated description) so Jira stays accurate. `docs/scope/scope.md` is the source of truth on any conflict.

## Rules

- When a feature in `docs/scope/scope.md` is marked `done` (by any skill, or directly by the engineer), commit that feature's changed files with a descriptive message and push to the tracking remote branch right after. No confirmation needed for this specific commit and push; other git operations still confirm as usual.
- Page sections live in `src/sections/` (Hero, Header, Badges, Projects, Skills, FAQs, Testimonials, Footer, Intro) and are composed in `src/app/(site)/page.tsx`. Other public routes live in `src/app/(site)/<route>/page.tsx` and reuse `Header` and `Footer` (e.g. `/products` composes `src/sections/Products.tsx`).
- Header and footer section links use `/#<section-id>` hrefs and call `scrollToSectionIfSamePage` from `src/lib/section-nav.ts`, so they smooth scroll on `/` and navigate home from any other route. Follow this for any new section link.
- `utils/data/products-data.ts` feeds the public `/products` page and holds public fields only (id, name, status, summary, links, plus an optional `standalone: true` set only for products standalone by design). Never add notes, lessons, stack, repo links, ticket keys, or client names there; the `PublicProduct` type rejects extra fields (spec 0002). The file is generated by the studio export (`/studio/systems/export`, spec 0008): edit systems in the studio, export, read the diff, and commit it rather than hand editing.
- Reusable UI primitives live in `src/components/ui/`, following shadcn/ui conventions (`components.json`: style "new-york", Radix-based, class merging via `cn()` in `src/lib/utils.ts`).
- The app has two route groups with their own root layouts: `src/app/(site)/` (public, with Header, Footer, Analytics) and `src/app/(studio)/` (the private studio). Both share `src/components/AppProviders.tsx` and the font in `src/lib/fonts.ts`. Studio conventions live in [src/studio/AGENTS.md](src/studio/AGENTS.md) (spec 0003).
- Public code (`src/app/(site)/`, `src/sections/`, `src/components/`) never imports from `src/studio/`, and no studio variable ever uses the `NEXT_PUBLIC_` prefix.
- Path alias `@/*` maps to `src/*`.
- Content/data lives in `utils/data/*.js` and `utils/data/*.ts` (badges, personal info, skills, products) and is imported into section components rather than hardcoded inline.
- Interactive client sections are marked `"use client"` at the top of the file (e.g. `Hero.tsx`).
- Dark/light theme handled via `next-themes` + `ThemeToggleButton`.
- File extensions are mixed (`.tsx` and `.jsx` both appear in `src/sections`, e.g. `Skills.jsx`); no enforced convention yet.

## Code graph (graphify)

`graphify-out/` holds a code only knowledge graph of this repo (built with `/graphify . --code-only`, structural parsing, no LLM cost). It is local and gitignored; each machine builds its own.

- **Read it before reading code broadly.** Start with `graphify-out/GRAPH_REPORT.md` (god nodes, communities, surprising connections), then ask by symbol name: `graphify explain "applyImportPlan()"` (callers and imports, with file and line), `graphify path "<A>" "<B>"`, `graphify query "<symbolA> <symbolB>" --budget 1500`. Plain English questions match poorly; function, file, and component names match well. Open only the files the answer points to.
- **The graph is a map, not the truth.** Edges marked `INFERRED` or `AMBIGUOUS` can be wrong (it matches some calls by name). Read the actual file before you edit or cite it.
- **Keeping it fresh:** a post commit hook (`graphify hook install`, chained by the Vault Radar dispatcher) re-extracts changed code files after every commit. Rebuild by hand with `graphify update .` (add `--force` after deleting files). `.graphifyignore` keeps it code only (docs, specs, and `.claude/` skills are excluded); without it, an update parses markdown headings into a thousand noise nodes. No `graphify-out/` yet? Read the code directly, the graph is optional.
- **Known gap:** the `drizzle/*.sql` migrations add nothing until the SQL parser is installed (`uv tool install "graphifyy[sql]"`); read `src/studio/db/schema.ts` for the schema.
